为什么先做 Harness Validation，再做 Desktop Runtime

前言

最近在实习开发中，我注意到一个很有意思的顺序：团队会先完成 Harness Validation，再进入 Desktop Runtime 的开发。

刚开始看时，我下意识觉得桌面端运行时才是“真正的产品”，应该优先做界面、进程管理和功能串联。但实际做下来才发现，先验证 Harness，能够更早回答一个关键问题：核心能力是否能被稳定地调用、观测和验证。

这篇文章记录的是一种通用的工程思路，不涉及具体项目、代码或内部架构。

两层分别解决什么问题

这里的 Harness 可以理解为一层受控的验证环境。它负责把核心能力包装成可重复调用的流程，并提供输入、输出、日志和结果校验。它关注的是：给定一份输入后，核心逻辑是否按预期工作。

Desktop Runtime 则更接近用户真正使用的运行环境。它还要面对窗口生命周期、进程通信、权限、资源占用、安装升级、异常恢复等问题。它关注的是：功能能否在真实桌面环境中长期、稳定地运行。

两者不是替代关系。Harness 负责先把“能力本身”验证清楚，Desktop Runtime 负责把验证过的能力交付给用户。

为什么先做 Harness Validation

1. 先缩小问题范围

桌面端出了问题时，原因可能来自业务逻辑、进程间通信、UI 状态、文件路径、系统权限，甚至不同操作系统的差异。如果核心逻辑还没有独立验证，排查会变成在很多层之间猜测。

Harness 提供一个更小、更可控的环境。先在这里跑通输入、处理和输出，之后 Desktop Runtime 出现问题时，就能更有把握地判断：问题是在运行时集成，还是在核心能力本身。

2. 更早建立可重复的验收标准

“我本地跑通了”通常不是一个足够可靠的结论。一个有效的验证流程至少要明确：

  • 输入是什么，边界条件有哪些；
  • 预期输出是什么，允许多大误差；
  • 失败时记录哪些日志和上下文；
  • 同一版本能否被其他人重复执行。

把这些内容放进 Harness 后，验证不再依赖某个人的本地环境或操作习惯。后续改动也能持续回归，避免一个看似无关的修改悄悄影响核心功能。

3. 降低桌面端的返工成本

桌面端的改动往往牵一发动全身。一个还没有稳定的接口，会让 UI、状态管理和进程通信反复调整；等核心逻辑改完，之前接入的部分又需要重新修改。

先通过 Harness 固化调用方式、数据格式和异常处理，再把它接进 Desktop Runtime，能让集成阶段的工作更聚焦。桌面端团队也能围绕一个更稳定的契约开发，而不是一边猜接口一边修逻辑。

4. 让 AI 能力更容易被评估

这点在 AI 应用里尤其重要。模型输出有时并非简单的“对”或“错”，还需要关注准确率、延迟、成本、稳定性，以及异常输入下的表现。

在桌面 UI 中观察这些指标并不方便；Harness 却可以批量输入样本、记录耗时、保留输出，再对结果做对比。这样，是否值得把某个 AI 能力接入产品，就不只凭直觉判断，而是有一组可追溯的数据作为依据。

一个简单的开发节奏

我目前更认同下面这个顺序：

  1. 明确核心能力的输入、输出和错误语义；
  2. 用 Harness 跑通最小闭环，并补充典型和异常场景；
  3. 将验证过程沉淀为可重复执行的检查；
  4. 在 Desktop Runtime 中接入已经验证过的能力；
  5. 再验证窗口、进程、权限和用户操作等运行时问题。

这个顺序并不意味着所有 UI 都要等到最后才开始。原型可以并行探索，但产品依赖的核心链路，最好先有独立、可重复的验证结果。

Harness 也不能替代真实运行时

Harness 验证通过，只能说明核心能力在受控环境里成立。它无法覆盖桌面端的所有问题，例如：

  • 多窗口或多进程下的状态同步；
  • 操作系统权限和文件系统差异；
  • 长时间运行后的内存、性能和恢复能力；
  • 用户打断操作、网络波动等真实使用场景。

所以正确的理解不是“做完 Harness 就完成开发”，而是先建立一个可信的基线，再把复杂度逐层引入。这样每一层出现问题时，我们都知道应该从哪里开始排查。

结语

先做 Harness Validation，再做 Desktop Runtime，本质上是在把复杂系统拆成两次验证：先证明核心能力可用，再证明它能在真实产品环境里可靠地运行。

对于需要频繁迭代的桌面应用，尤其是带有 AI 能力的产品，这个顺序能让开发过程更可控，也能让后续的优化有明确的依据。
